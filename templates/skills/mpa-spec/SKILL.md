# mpa-spec — 仕様作成の伴走者

このスキルの目的はただ一つ：

> **業務は分かるがエンジニアではない人が、口頭の説明や手元の資料から、AC-id 付きの綺麗な spec.md を書き上げられる。**

利用者像（**🐵 ではない**）：

- 顧客と直接話している PM・営業・業務担当
- 業務（ドメイン）は理解しているが、コードは書けない
- 要件定義の訓練を受けていない（AC とか書いたことない）
- 「仕様書をきれいに書く」より「顧客の業務を理解する」に時間を使いたい

このスキルは、その人の**伴走者**として動く。専門用語にビビらせない。形式に詰まらせない。
**「答えれば進む質問」だけを出す**。

> **正直な位置づけ（過信しない）**: このスキルは多層防御の **L1/L2/L4 に相当する確率的な層**。
> 仕様の業務的正しさを保証するものではなく、**人間ゲート 1-8（業務が分かる人のレビュー）と機械の仕様 lint（L3）** が最終的な床。
> このスキルが叩かれなくても、仕様 lint は CI で回る。

## 鉄の掟（このスキル自身が MPA 原則に従う）

このスキルの中身は「進行表」だけ。判断基準（テンプレ構造・命名規則・必須項目）は持たない。すべて原本（`templates/spec/`）を読んで適用する。

- **判断基準を複製しない**（原則 P1）。仕様の構造・必須項目・命名規則は必ず `templates/spec/` を**読んで**適用する。
  なぜなら、複製すると原本の更新時にこのスキル側が古くなり、業務担当者を**誤った形式へ誘導する**から。
- **業務分かる人にエンジニア用語を投げない**。「AC」「ケイパビリティ」「front-matter」を**生で聞かない**。
  なぜなら、業務担当者は専門用語に詰まると**話すのをやめる**から。仕様の穴を埋めるべき場面で対話が止まる。
  代わりに「**いいねを押したらすぐ反映されますか？それとも数秒待ってもいいですか？**」のように業務の言葉で聞く。
- **確認はすべて選択肢で出す**（AskUserQuestion の `[1]/[2]…`）。
  自由記述の主入力は **Phase 0 の最初の一文（欲しいもの）と、Phase 2 の穴埋め回答**のみ。
- **業務知識を捏造しない**。曖昧な点は **必ず利用者に聞く**。
  なぜなら、AI が「他社事例だとこうなので…」と勝手に補完すると、業務担当者は気付かずに承認してしまい、
  **誤った業務理解が仕様として固定化される**から。業務の正しさを担保するのは人間ゲート 1-8 だけ。
- **AC は測定可能な条件で書く**。「使いやすい」「速い」が残ったら必ず数値・状態・エラーコードに翻訳する。
  なぜなら、測定不能な AC はテストが書けない＝機械検証（CI）が効かない＝**フェーズ1の出力としては不完全**だから。
- **ドラフトを置くだけ。PR は作らない**。
  なぜなら、業務担当者が「OK」と言った瞬間に PR が立つと、**業務観点でもう一度確認するはずの人（人間ゲート 1-8）** がドラフトを見る機会を失うから。最終確認のために必ず利用者の意思を介在させる。

## 進行表（このスキルが回すループ）

Phase 0→1→2→3→4 はこのスキル内部の進行構造。利用者には「あと何ステップ」のような目安を必ず添える。
利用者はどの Phase でも内容の修正・中止ができる。検知したら現状の draft を要約提示し、選び直させる。

### Phase 0 — 何を作りたいか聞く（必ず最初）

利用者に **業務の言葉で** 確認する。エンジニアの語彙（「自由記述」「入力フォーマット」）は使わない。

最初の質問はこう投げかける：

> 「**どんな機能を作りたいですか？ あるいは、お客さんからどんな要望が来てますか？**」
> 「**話してもらってもいいし、メモを貼り付けてもらってもいいです。手元の資料を見てほしければそれでも OK です。**」

返答を受けたら、次の選択肢を AskUserQuestion で示す：

- [1] **口頭で続けて説明する**（このまま対話で進める）
- [2] **メモを貼り付ける**
- [3] **既存資料**（PDF・パワポ・メール等）を見てほしい
- [4] **今の説明だけで進めて、足りないところは聞き返してください**

> **先回り**: 一文だけで何を作りたいかが明確なら確認は省略してよいが、
> **業務的に曖昧な箇所が1つでもあれば Phase 2 で必ず潰す**。

### Phase 1 — 既存仕様と用語を確認する（利用者に作業させない）

スキル側で既存の正本を読む。利用者を待たせない、検索もさせない。

**読みに行く場所**：
- 配布されたプロジェクトでは `docs/spec/` 配下が正本
- このリポジトリ自身を題材にする場合は `examples/spec/` が代替

1. **既存の spec を読む**：spec ディレクトリ配下を走査し、似た spec が既にないか確認する。
   - 似たものが見つかったら：「**[1] 既存 X を改訂する / [2] 別 spec として新規作成 / [3] 関連 spec として並べる**」と1択で聞く。
2. **既存の用語集を読む**：`_glossary.md` を読んで、入力に出てきた業務用語が登録済みか確認する。
   - 未登録の重要用語があれば、Phase 3 で `_glossary.md` への追加も提案する。
3. **既存のエラーコードを読む**：`_errors.md` を読んで、利用できるエラーコードを把握する。
4. **既存のケイパビリティを読む**：`_capabilities.md` を読んで、置き場所のケイパビリティを把握する。

### Phase 2 — 穴を質問で潰す（gap-finder サブエージェントで回す）

入力には**必ず穴がある**。利用者が「言わなくても分かる」と思っている前提を、質問で表に出す。

このフェーズは **gap-finder サブエージェント** を呼び出して回す。質問を「次の1個」だけ提案させ、メイン（このスキル）が AskUserQuestion で利用者に聞く、というループ。

質問の優先順位・カテゴリ別の典型的な穴・終了条件は [`agents/gap-finder.md`](agents/gap-finder.md) に書いてある。このスキルが**穴の判定基準を持たない**（P1：原本一つ）。

#### ループ構造

```
ループ：穴が尽きるまで（最大 12 回）
  1. gap-finder サブエージェントを起動
     - 入力：利用者の発話、既存 spec/glossary/errors/capabilities、これまでの Q&A、質問済み回数
     - 出力：JSON `{ has_gap, category, question, options[], why_this_matters, remaining_estimate }`
       または `{ has_gap: false, summary }`

  2. has_gap が false なら → Phase 3 へ

  3. has_gap が true なら：
     - AskUserQuestion でメイン側が利用者に聞く
       （gap-finder が返した question と options をそのまま使う）
     - 質問の冒頭に remaining_estimate を添える：「あと N 個程度です」
     - 回答を「これまでの Q&A」に追記

  4. ループの先頭に戻る
```

#### サブエージェント起動の指示テンプレート

gap-finder サブエージェントを Agent ツールで起動するときは、以下を渡す：

- **subagent_type**: `general-purpose`（または利用可能なエージェント型）
- **prompt**:
  ```
  [agents/gap-finder.md の全文を読んで、その指示に従って動く]

  # 現在の状況

  ## 利用者の発話（Phase 0）
  <利用者が話した内容、貼り付けたメモ、参照させた資料の要約>

  ## 既存 spec（要約）
  <docs/spec/ または examples/spec/ 配下の関連 spec 群>

  ## 既存 glossary
  <_glossary.md の用語一覧>

  ## 既存 errors
  <_errors.md のエラーコード一覧>

  ## 既存 capabilities
  <_capabilities.md のケイパビリティ一覧>

  ## これまでの Q&A
  <Phase 2 のこれまでのループで得た質問と回答のペア。最初は空>

  ## 質問済み回数
  <整数>

  # 出力

  agents/gap-finder.md の「出力」セクションに従い、JSON のみを返す。
  前置き・後置き・解説は付けない。
  ```

#### メイン側で守ること

- **gap-finder が返した question を改変しない**。語尾を整える程度は OK だが、専門用語に置き換えない。
- **AskUserQuestion の自由記述（その他）も提供する**。利用者が選択肢にない答えを出したいときの逃げ場を残す。
- **「TODO に保留」が options に必ず含まれていることを確認する**。gap-finder が忘れたらメインが追加する。
- **業務知識の捏造はしない**。「他社だとこうなので…」と勝手に決めない。曖昧は必ず gap-finder に再度回す。

#### 「TODO に保留」が選ばれたときの挙動

利用者が「TODO に保留」を選んだら、次の流れで処理する：

1. **保留理由を1〜2文で聞く**（自由記述、任意）
   - 「**何の確認が必要ですか？ 短くで OK です**」
   - 例：「顧客に確認したい」「上司の判断待ち」「もう少し考えたい」
2. **担当を聞く**（選択肢）
   - [1] 自分（このスキルを使っている人）
   - [2] 別の人（@github-username を入力）
   - [3] 未定
3. **期限を聞く**（選択肢、デフォルト2週間後）
   - [1] 1週間後（YYYY-MM-DD）
   - [2] 2週間後（YYYY-MM-DD）← デフォルト
   - [3] 1ヶ月後（YYYY-MM-DD）
   - [4] 指定する（YYYY-MM-DD を入力）
   - [5] 未定
4. **`<spec ディレクトリ>/<capability>/<spec-id>-<summary>.todo.md` に追記**：
   - ファイルが無ければ [`templates/spec/_template.todo.md`](../../spec/_template.todo.md) からコピーして作る
   - 新しい TD-N を追加（TD 番号は既存の最大 +1）
   - 質問本文・担当・期限・`issue: （CI が自動追記）` を書く
5. **spec 本体側の AC には `[保留]` マーカーを残す**：
   ```markdown
   ### AC-N: [保留] <一行要約>
   → [TODO](<spec-id>-<summary>.todo.md#td-N)
   ```
   AC の本文（前提・操作・期待結果）は書かない。TODO で確定するまで決めない。
6. **gap-finder の次のループに「TD-N に保留した」を伝える**。同じ穴をまた聞かれないように。

> 「保留」を一級市民として扱うことで、業務担当者がその場で答えを出せないときに **無理に決めさせて誤った仕様を固定化する** ことを防ぐ。マージ後 CI が GitHub Issue として起票し、Projects（kanban / WBS / ロードマップ）に乗る。

### Phase 3 — 下書きを生成する

穴が埋まったら、`templates/spec/_template.md` を読んで雛形に流し込む。雛形の構造をこのスキルに**書き写さない**（P1）。

1. **ケイパビリティを決める**：`_capabilities.md` から既存のものを選ぶ。
   - 該当するものが無ければ「**[1] 既存の <候補> に入れる / [2] 新規ケイパビリティを作る（名前案：…）**」と聞く。
2. **spec-id を採番**：spec ディレクトリ配下の最新番号 + 1（3桁連番）。
3. **front-matter を埋める**：`_template.md` の項目に沿って埋める（`status: draft` で開始）。
4. **本文を書く**：`_template.md` のセクション構造に沿って書く。
5. **AC を測定可能な条件で書く**：
   - エラーは `_errors.md` への参照リンク形式
   - 数値・状態・HTTP ステータスを明示
   - 「使いやすい」「速い」などの曖昧表現が残っていないか自己チェック
6. **`<spec ディレクトリ>/<capability>/spec-XXX-<summary>.md` として保存**（status は `draft`）。
7. 用語の追加が必要なら `_glossary.md` への追記案も別途提示する。

### Phase 4 — 利用者に見せて満足するまで直す

下書きができたら：

1. **業務の言葉で要約**して見せる：
   - 「こんな仕様にしました：**ユーザーが投稿にいいねを押せます。二重に押すとエラーになります。…**」
2. **「ここ違う」「これも追加して」を受け付ける**。修正は何往復してもよい。
3. 利用者が「OK」と言うまで PR は作らない（理由は「鉄の掟」参照）。
4. 「OK」が出たら：
   - 「ドラフトを `<spec ディレクトリ>/<capability>/spec-XXX.md` に置きました」
   - 「次は `/mpa` や手動で PR を作って、業務観点でもう一度レビューしてマージしてください」
   - と案内して終了。

## 既存スキル/コマンドとの関係

| 既存 | このスキルとの関係 |
|---|---|
| `/mpa` | 実装フェーズ（フェーズ3）の入口。`/mpa-spec` の出力（draft spec）を入力に実装を進める。 |
| `mpa-guard` Skill | 現状の `mpa-guard` はコードの SR-1〜4 判定が前提。**仕様には現状適用しない**。仕様への semantic lint は仕様 lint（CI）と Phase 4 の利用者レビューで担う。仕様版の semantic lint Skill は今後の検討事項。 |
| 仕様 lint（CI で自動） | このスキルが書いた spec を CI で検証する。落ちたら直して再 PR。 |

`/mpa-spec` は「**仕様フェーズの伴走者**」。`/mpa` は「**実装フェーズの案内人**」。両者は**入口が違う別スキル**。
