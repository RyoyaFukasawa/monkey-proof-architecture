# mpa — 作業の推奨入口（対話オーケストレータ）

このスキルの目的はただ一つ：

> **ユーザーが MPA を知らなくても、これと対話するだけで MPA の手順に沿って実装/修正を進められる。**

ユーザーは constitution を読まない。SR-1〜4 を覚えていない。FSD/CleanArch の配置も知らない。
**それでいい。** このスキルが代わりに考え、ユーザーには「答えれば進む質問」だけを出す。

> **正直な位置づけ（過信しない）**: このスキルは多層防御（[`constitution/50-enforcement.md`](../../../constitution/50-enforcement.md)）の
> L1/L2/L4 に相当する**確率的な層**であり、生成と同一 AI・同一基準で動くため盲点が相関する（同 50-enforcement の但し書き参照）。
> 「対話するだけで SR 違反ゼロ」を保証するものではない。**絶対の床は L3（CI の機械検証）と L4 の人間判断**にある。
> このスキルが叩かれなくても、hook（L1/L2）と CI（L3）は機能する。

## 鉄の掟（このスキル自身が MPA 原則に従う）

- **判断基準を複製しない（P2）**。SR の中身・配置ルール・閾値（3回ルールの「3箇所」等）は必ず `constitution/` を**読んで**適用する。
  このファイルは「どの順で・何を聞くか」という**進行表**であって、ルールの実体ではない。
- **迷わせない（Monkey-Proof）**。ユーザーに「どのレイヤー？」と生で聞かない。
  こちらが候補を絞り、**選ぶだけ/答えるだけ**の形で聞く。
- **確認はすべて選択肢で出す**。AskUserQuestion を使い `[1]/[2]…` の形で聞く。
  自由記述の主入力は **Phase 0 の最初の一文（やりたいこと）のみ**。
  選択肢に添える短い理由（「理由：…」「理由を一言」等）は、選択を補う**任意の付記**として可。
- **ステップ感を添える**。確認のたびに「あと1つ確認したら実装に入ります」のように残りの目安を一言添える。
- **勝手に突き進まない**。配置やリスクで判断が割れたら、**断定せず選択肢で聞く**。
- **SR の判定実行は `mpa-guard` に委ねる**。このスキルは進行を回す側。SR-1〜4 の判定が要る場面では
  `mpa-guard` を起動し、その結果を対話に乗せる（基準は両者とも constitution が単独所有）。

## 進行表（このスキルが回すループ）

> Phase 0→1→2→3 はこのスキル内部の進行構造。**枝はネストしうる**（修正中に小さな新規が要る等）。
> その場合は**親 intent を保ったまま**子の枝を当該レイヤーに限定して回し、終わったら親に戻る。
> 「Phase 0 に戻す」は intent を選び直すこと（AskUserQuestion の再実行）であって、**書いたコードは破棄されない**。
> ユーザーはどの Phase でも intent の変更/中止ができる。検知したら現在の差分を要約提示し、
> 「破棄して新 intent へ / 退避して後で戻る」を選ばせて Phase 0 から再開する。

### Phase 0 — intent を一つに決める（必ず最初）

ユーザーに確認する（AskUserQuestion を使い、選ぶだけにする）：

1. **何をしたい？** 一文で（ここだけ自由記述可）。
2. **作業の種類は？**
   - **新規実装** — まだ無い機能を作る
   - **既存修正** — 既にあるものを直す/変える（バグ修正・仕様変更）
   - **リファクタ/共通化** — 動作を変えずに構造を整える・重複をまとめる

intent が決まったら、対応する Phase 1 の枝へ進む。

> **先回り（Monkey-Proof）**: ユーザーの一文から intent が明らかなら、確認のため「これは『新規実装』ですね？」と
> **1択提示**して即進んでよい。ただし**確定の前に、対応する枝の対象特定を先に走らせる**
> （例：修正なら該当コードが実在するか先に確認）。実在して初めて intent を確定する＝誤分類の手戻りを減らす。
>
> **複数 intent が混ざる一文**（例「新機能を足しつつ既存も整理」）なら、こちらが作業を分解し
> 「これは2つの作業に分かれます。(1)… (2)…。どちらから？」と**順序を1択で聞く**。
> 同時混在はさせず順次処理する（SR-2 の精神）。引いた Capability Map・特定済みファイル等の作業文脈は枝をまたいで保持する。

### Phase 1 — intent 別に MPA 手順を代行運転

どの枝でも、**基準は読みに行く**。手順の実体は constitution 側にある：

- 生成時手順: [`constitution/checklists/before-writing.md`](../../../constitution/checklists/before-writing.md)
- SR 本体: [`constitution/20-semantic-rules.md`](../../../constitution/20-semantic-rules.md)
- 探し方: [`constitution/40-discovery.md`](../../../constitution/40-discovery.md)
- 配置: [`constitution/10-structure.md`](../../../constitution/10-structure.md)

> **どの枝でも全 SR は constitution 側で毎回適用される**（before-writing の全 STEP）。
> 各枝の「特に効く SR」は、対話で**どこを重点的に問うか**の指針であって、他の SR を免除するものではない。

#### 枝A：新規実装 → 特に SR-1（重複禁止）が効く

1. やりたいことを「動詞 + 目的語」に翻訳し、**[1] これで合っている / [2] 違う（修正）** で確認する。
2. **Capability Map を自分で引く**（`40-discovery.md`）。ユーザーには探させない：
   関連レイヤーの公開 `index.ts` を読む → `shared` / `application/shared` を直接走査 → 不足なら `find-shared` Skill。
3. 近い既存が見つかったら、**ユーザーに見せて選ばせる**（汎用語で大量ヒットしたら「動詞+目的語」を絞り直す）：
   「既存の X が近いです。**[1] そのまま再利用 / [2] 拡張（引数等で差分を吸収）/ [3] 別物として新規（理由：…）**」
   - [2] 拡張を選んだら、SR-2（拡張後も責務が接続詞なしの一文で言えるか）を即チェックする。
4. 新規で行くと決まったら、**配置を自分で決めて1択提示**：「これは features/<動詞> に置きます。よいですか？」
5. SR-2/SR-4 の判定が要る場面は `mpa-guard` を起動して確認する（ユーザーに自己点検させない）。
6. 実装後、slice の `index.ts` に公開する（Capability Map が自動更新される）。→ Phase 2 へ。

#### 枝B：既存修正 → 特に SR-2/SR-4 が効く

1. 直す対象を特定する（ユーザーの説明から、自分で該当ファイルを探して提示・確認）。
   - **対象が見つからない場合**：「その機能は見当たりません。実は未実装かもしれません。
     **[1] 新規実装として作る（枝Aへ）/ [2] 別の箇所を指す**」と1択で確認する。
2. 純粋に既存の振る舞いを直すだけなら、SR-1 の探索は**実質ヒットしないだけ**（スキップではない）。
   **ただし修正の中で新しい関数/ユースケース/機能を足す瞬間が来たら、新ファイルかどうかに関わらず
   SR-1（Capability Map / `40-discovery.md`）を必ず引く**。
3. **SR-2 を見張る**：「ついでに別の責務を足していないか？」を自分で監視。
   足しそうになったら「それは別の作業です。**[1] 今の修正に含める / [2] 別作業（新規/リファクタ）として分ける**」と聞く。
4. **SR-4 を見張る**：直すために domain/entities に HTTP/DB の語彙を持ち込んでいないか自分で監視。
5. 配置は変えない（既存の場所で直す）。→ Phase 2 へ。
6. **派生サブタスクの検知**：修正の中に新規/リファクタが内在するなら、Phase 0 へ巻き戻さず、
   親 intent（修正）を保ったまま、必要な枝の SR チェックを当該レイヤーに限定して回し、親の修正に戻る。
   修正の範囲を大きく超える（別機能の新設等）なら「これは修正の範囲を超えています。
   **[1] 新規実装/リファクタとしてやり直す / [2] このまま続ける**」と Phase 0 への差し戻しを聞く。

#### 枝C：リファクタ/共通化 → 特に SR-3（早すぎる共通化）が効く

1. 対象の2つ(以上)を取り出す。
2. **こちらが先にコードを読み、根拠つきの推定を具体名で提示する**（抽象語をユーザーに投げない）：
   「この2つは同じ〈具体的なルール名〉から来ているので、まとめても安全に見えます。
    **[1] その推定でOK / [2] 違う（今たまたま似てるだけ。理由を一言）**」
   ※ 判定基準（SR-3 の「同じ理由で同時に変わるか」）は `20-semantic-rules.md` を読んで適用する。
3. [1]（本質的同一）なら共通化先レイヤーを自分で決めて1択提示（shared か entity 寄せか等）。
4. **[2]（偶然の一致/判定不能）だった2箇所目のとき**だけ、SR-3 の3回ルール（`20-semantic-rules.md` を読んで適用）に照らし
   「まだ早い。3箇所目が来てから」と止める提案をする。本質的同一（step2 で [1]）なら step3 へ進み、ここで止めない。
5. SR-2（共通化で責務が混ざらないか）を `mpa-guard` で確認。→ Phase 2 へ。
6. **バグの混入検知**：リファクタ中に動作の誤り（バグ）を見つけたら、それは別 intent（修正）。
   今のリファクタに混ぜず「**[1] 別作業（修正）として分ける / [2] このリファクタに含める**」を確認する。
7. **共通化しないと着地したとき**（step2 で [2]、または step4 で止めたとき）：
   「今回は分けたまま進めます。**[1] 元の作業（修正/新規）に戻る / [2] ここで終了**」と締める。

### Phase 2 — 実装する（全枝の合流点）

- 上の枝で「進んでよい」が確定したら、実装する。
- 実装中も SR-2/SR-4 を見張り続ける（判定が要れば `mpa-guard`）。ユーザーには成果と判断ポイントだけ見せる。

### Phase 3 — 終了時に自己レビュー（before-merge を代行）

実装が一区切りしたら、ユーザーに促されなくても自分で：

1. [`constitution/checklists/before-merge.md`](../../../constitution/checklists/before-merge.md) に沿って R-1〜R-4 を点検
   （判定実行は `mpa-guard` / `find-shared` を使う）。
2. 確度「高」の SR 違反があれば直す。グレーは**断定せずユーザーに判断を仰ぐ**。
3. 「実装できました。MPA 観点で確認した結果：…」と簡潔に報告する。

> **この自己レビューは生成と同一文脈・同一 AI なので盲点が相関する**（[`50-enforcement.md`](../../../constitution/50-enforcement.md) の但し書き）。
> 確度高の明確な違反を拾う網であって、独立した保証ではない。可能なら**生成時の意図を一旦伏せて diff を読み直す**と相関がわずかに下がる。
> 最終的なマージ判断は人間（L4）と CI（L3）に委ねる（before-merge.md の通り）。

## 既存スキル/コマンドとの関係（複製しない）

| 既存 | このスキルでの位置づけ |
|---|---|
| `/mpa-check`（生成時セルフチェック） | 枝A/Phase1 の中身。`/mpa` がこの手順を**対話で代行**する。 |
| `/mpa-review`（レビュー時チェック） | Phase 3 の中身。`/mpa` が終了時に**自動で**通す。 |
| `mpa-guard` Skill | **SR 判定の実行器**。`/mpa` は進行を回し、SR-1〜4 の判定はこれを起動して行わせる。 |
| `find-shared` Skill | SR-1/SR-3 の意味検索の実行器。枝A/枝C で `/mpa` が呼ぶ。 |

> `/mpa` は「人間の作業フロー全体の案内人（オーケストレータ）」。
> 既存の check/review/guard は「特定フェーズの実行器」。`/mpa` がそれらを順に運転する。

## メタルール（constitution と同じ）

- 根拠なき指摘・断定をしない。グレーは人間に委ねる。
- ルールを増やさない。SR-1〜SR-4 のみ。
- 基準は常に `constitution/`。このスキルが古くなっても constitution が真実。
