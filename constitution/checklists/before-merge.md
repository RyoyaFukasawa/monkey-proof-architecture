# Checklist — Before Merge（レビュー時ダブルチェック）

> **いつ**: PR / diff をマージする前。
> **誰**: AI（レビュアー役）＋ 人間レビュアー。
> **目的**: P4 の「事後」側。生成時にすり抜けた意味的違反を、diff に対して捕まえる。
>
> このチェックは [`../20-semantic-rules.md`](../20-semantic-rules.md) の基準で行う。基準をここに複製しない。

---

## 入力

- レビュー対象: 現ブランチの diff（`git diff <base>...HEAD`）。
- 追加 / 変更されたファイルの一覧と中身。

---

## 機械検証の確認（P3 / 先に通っている前提）
- [ ] lint（FSD / CleanArch 依存方向・命名・deep import 禁止）が green。
  - red なら、それは機械が落とす範囲。AI レビューはそこを再判定しない。**機械の結果を信頼する。**

---

## 意味レビュー（P4 / AI が担う本体）

### R-1（SR-1）重複の検出
- [ ] 追加された関数 / コンポーネント / ユースケースを列挙した。
- [ ] それぞれについて、**`find-shared` Skill** でリポジトリ全体と意味照合した
      （Capability Map = 公開 `index.ts` ＋ shared 系の直走査 も併せて確認 → [`../40-discovery.md`](../40-discovery.md)）。
- [ ] 重複候補があれば「新規 X は既存 Y と重複の可能性。理由：…」と**根拠つきで指摘**した。

### R-2（SR-2）単一責務の検出
- [ ] 追加 / 肥大化したファイルの責務を一文で要約した。
- [ ] 「〜と〜」が必要なファイルを**分割候補として、割る位置つきで**指摘した。
- [ ] 過剰分割（凝集した概念の分断）も逆方向の指摘として見た。

### R-3（SR-3）早すぎる共通化の検出
- [ ] この diff で**新たに共通化**された箇所はあるか？
- [ ] あれば「同じ理由で変わるか」を問い、**偶然の一致を共通化していないか**を指摘した。
- [ ] 逆に、本質的同一なのに重複放置（SR-1 違反）もないか見た。

### R-4（SR-4）語彙汚染の検出
- [ ] domain に HTTP / DB / FW / UI 語彙の漏れがないか（`statusCode`, `req`, `@Column` 等）。
- [ ] application にインフラ詳細の漏れがないか。
- [ ] entities に技術詳細の漏れがないか。
- [ ] 漏れを「概念 X がレイヤー Y に漏れている。該当：file:line」と指摘した。

---

## 出力フォーマット（AI レビューの返し方）

各指摘は必ず以下を含む：

```
[SR-N] <一行サマリ>
  - 該当: <path>:<line>
  - 根拠: <なぜ違反か。意味的説明>
  - 提案: <どう直すか。再利用 / 分割位置 / レイヤー移動 など>
  - 確度: 高 / 中 / 低（低～中は「判断を仰ぐ」）
```

- **確度「高」**: 明確な違反。修正を強く推奨。
- **確度「中・低」**: グレー。**断定せず人間に判断を委ねる**。

---

## 通過条件

- 確度「高」の SR 違反が **0 件**。
- 確度「中・低」は人間レビュアーが確認済み。
- 機械検証（lint）が green。

→ マージ可。

> **メタルール**: 根拠を示せない指摘はしない。グレーは断定しない。
> MPA のレビューは「人間の最終判断を助ける」もので、置き換えるものではない。
