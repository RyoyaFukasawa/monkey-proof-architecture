# Checklist — Before Writing（生成時セルフチェック）

> **いつ**: AI がコードを**書き始める前**、および新しいファイル/機能を追加する前。
> **誰**: AI（人間も新規実装前に読む）。
> **目的**: P4 の「事前」側。書く前に止まって、意味的ルール（SR-1〜SR-4）に照らす。
>
> このチェックは [`../20-semantic-rules.md`](../20-semantic-rules.md) の基準で行う。基準をここに複製しない。

---

## 手順

### STEP 0. 置き場所の確認（機械検証側 / P3）
- [ ] これは web（FSD）か api（CleanArch）か、どのレイヤーに属するか？
- [ ] FSD なら：app / pages(URLルート) / widgets / features(動詞) / entities(名詞) / shared のどれか確定したか？
      （read→entity / 変更→feature。判断に迷うなら [`../10-structure.md`](../10-structure.md) の「apps/web — FSD」を読む）
- [ ] CleanArch なら：domain / application / infrastructure / presentation のどれか確定したか？
- [ ] 配置に迷ったら [`../10-structure.md`](../10-structure.md) を読む。**迷ったまま書かない。**

### STEP 1. SR-1：もう存在しないか？（重複チェック）
- [ ] 作る機能を「動詞 + 目的語」で一文にした。
- [ ] **Capability Map を引いた**（[`../40-discovery.md`](../40-discovery.md)）：
      関連レイヤーの公開 `index.ts` を読み、既存シンボルと突き合わせた。
- [ ] `shared` / `application/shared` は `index.ts` を持たないので、ディレクトリ内のファイル名・export を
      **直接走査**した（例: `apps/web/src/shared/**`、`apps/api/src/application/shared/**`）。
- [ ] 公開 API・ファイル走査で拾えなければ **`find-shared` Skill** で意味的類似を広く探した。
- [ ] 近い既存を最大 3 件挙げ、「再利用できないか」を自問した。
- [ ] 再利用できる → **新規作成をやめて既存を使う**。
- [ ] 再利用できない → **理由を一文で記録した**上で新規作成し、**slice の `index.ts` に公開した**。

### STEP 2. SR-3：共通化すべきか／すべきでないか
- [ ] 既存と似ているなら、「**同じ理由で同時に変わるか**」を問うた。
- [ ] YES → 本質的同一。共通化 or 再利用（SR-1 へ）。
- [ ] NO → 偶然の一致。**共通化せず、別物として書く**。
- [ ] まだ 2 箇所目なら、原則**共通化しない**（3 回ルール）。

### STEP 3. SR-2：1 ファイル 1 責務で書けるか
- [ ] これから書くファイルの責務を**接続詞なしの一文**で言える。
- [ ] 「〜と〜」が必要なら、**最初から分けて**設計する。
- [ ] CleanArch なら「1 ユースケース = 1 ファイル」を守る。

### STEP 4. SR-4：レイヤーの語彙を守れるか
- [ ] domain に HTTP / DB / FW / UI の語彙を持ち込まない設計になっている。
- [ ] エラーはドメインエラーで投げ、HTTP 変換は presentation に任せる設計か。
- [ ] entities が技術詳細（localStorage 等）を直接触らない設計か。

### STEP 5. 命名（P3）
- [ ] [`../30-naming.md`](../30-naming.md) の接尾辞・ケースに従う名前にした。

---

## 通過条件

上記すべてにチェックが付き、特に：
- SR-1 で**重複がない**ことを確認した（or 既存を使うことにした）
- 配置レイヤーが**一意に決まった**

→ 書き始めてよい。

**一つでも「迷い」が残るなら、書く前に人間に確認する。** MPA は「迷ったら書く」を許さない。
