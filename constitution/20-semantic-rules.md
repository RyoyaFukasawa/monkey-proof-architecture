# 20. Semantic Rules — 機械で縛れないルール集（MPA の心臓）

> このファイルは **P4** の本体。
> ここに書かれたルールは **AST / lint では原理的に判定できない**。意味理解を要する。
> よって **AI が生成時（before-writing）とレビュー時（before-merge）の両方で判定**する。
>
> Skill / slash command は判断基準をここからコピーしない。**このファイルを読んで、ここの基準で判定する。**

---

## 共通の考え方

各ルールは以下の形式で定義する：

- **Rule**: 一文で言えるルール本体。
- **なぜ機械で縛れないか**: lint/型で不可能な理由。
- **AI の判定手順**: AI が踏むべき具体的ステップ。
- **判定例**: ✅ OK / ❌ NG / ⚠️ グレー。
- **グレーゾーンの扱い**: 自信が持てないときどうするか。

> **重要原則**: AI は「違反だ」と断定する前に、**根拠（どのファイルの何行目か、なぜそう判断したか）を必ず提示する**。
> 根拠を示せない指摘はしない。意味判断は誤りうるので、最終決定は人間に委ねる前提で「指摘＋根拠」を出す。

---

## SR-1. 同じ機能を二度作らない（重複の禁止）

**Rule**: 新しい機能を書く前に、**意味的に同じ機能が既に存在しないか**を必ず確認する。存在するなら再利用する。

### なぜ機械で縛れないか
「同じ機能」は**意味的同値**であり、名前・シグネチャ・実装が違えば構文的には一致しない。
`formatDate` と `toDisplayDate` と `humanizeTimestamp` が同じことをしていても、grep では見つからない。

### AI の判定手順（生成時）
1. これから作る機能を**動詞 + 目的語**で一文に要約する（例：「日付を表示用文字列に変換する」）。
2. その意味で、既存コードを探す。**探し方の詳細（優先順位・shared 系のファイル走査・保証範囲）は
   [`40-discovery.md`](./40-discovery.md) を唯一の典拠とする**（ここに複製しない）。
   要点だけ：公開 `index.ts` の集合＋`shared`/`application/shared` のファイル直走査が索引（Capability Map）。
3. 公開 API・ファイル走査で拾えなければ、**`find-shared` Skill** を起動して意味的類似を広く拾う。
4. 近いものを **3 件まで列挙**し、それぞれについて「これで代替できないか？」を自問する。
5. 代替できる → 既存を使う（または拡張する）。新規作成しない。
6. 代替できない → **なぜできないかを一文で記録**してから新規作成し、その slice の `index.ts` に公開する
   （= Capability Map が自動更新され、次に同じものを作ろうとする人が STEP 2 で見つけられる）。

### AI の判定手順（レビュー時）
- 追加された関数 / コンポーネント / ユースケースについて、リポジトリ内に意味的に重複するものがないか検索し、あれば指摘する。

### 判定例
- ❌ `entities/user/lib/formatUserName.ts` があるのに `features/profile/lib/displayName.ts` で同じ整形を再実装。
- ✅ 既存の `formatUserName` を import して使う。整形要件が違うなら、**引数で差分を吸収できないか**先に検討。
- ⚠️ 似ているが「表示用」と「ソート用」で目的が違う → これは SR-3 と表裏。**偶然の一致なら分けてよい**（SR-3 参照）。

### グレーゾーンの扱い
- 「同じに見えるが目的が違う」場合は **SR-3** で判断する。
- 自信がなければ「重複の可能性あり：既存 X と新規 Y、判断を仰ぐ」と**人間に提示**する。断定しない。

> 関連: 既存の探し方は [`40-discovery.md`](./40-discovery.md)（Capability Map）。
> 意味的類似の深い探索は `find-shared` Skill を実行器として使う。

## SR-2. 1 ファイル 1 責務（単一責任）

**Rule**: 1 ファイルは **1 つの責務**だけを持つ。「このファイルは何をするか」を**接続詞なしの一文**で言えること。

### なぜ機械で縛れないか
「責務」は構文では数えられない。行数でもクラス数でもない。
500 行でも単一責務のファイルはあるし、20 行で 3 責務のファイルもある。**意味の凝集度**の問題。

### AI の判定手順
1. ファイルの責務を**一文で要約**してみる。
2. その一文に「**〜と〜**」「**および**」「**かつ**」のような**接続詞が必要なら、責務が複数**である疑い。
   - 例：「ユーザーを取得する**と**通知を送る」→ 2 責務 → 分割候補。
3. ただし以下は **1 責務とみなす**（過剰分割を避ける）：
   - 1 つの凝集した概念に属する複数の小関数（例：`Post` 集約のメソッド群）。
   - 1 コンポーネントとその専用サブコンポーネント。
4. 分割すべきと判断したら、**どこで割るか（どの責務を別ファイルへ）**を提示する。

### レイヤー別の「責務」の目安
- **FSD**: 1 slice = 1 機能。slice 内の 1 ファイルは 1 つの ui / model / api の関心事。
- **CleanArch**: **1 ユースケース = 1 クラス = 1 ファイル**（`LikePostUseCase`）。
  - ユースケースに「と」が出たら、それは複数ユースケース。
- **domain**: 1 ファイル = 1 集約ルート / 1 値オブジェクト / 1 ドメインサービス。

### 判定例
- ❌ `UserService.ts` が「認証**と**プロフィール更新**と**メール送信」を持つ。
- ✅ `AuthenticateUserUseCase.ts` / `UpdateProfileUseCase.ts` / `SendEmailUseCase.ts` に分割。
- ⚠️ `Post.ts` が `like()` `unlike()` `archive()` を持つ → **集約として 1 責務**。分割しない。

### グレーゾーンの扱い
- 「凝集した概念の複数メソッド」と「複数責務」の境界は意味判断。
- 迷ったら **「この一文に接続詞が要るか」**に立ち返る。要らなければ 1 責務。

## SR-3. 早すぎる共通化をしない（誤った DRY の禁止）

**Rule**: 共通化は、**本質的に同一**なものだけに行う。**偶然似ているだけ**のものを共通化しない。

### なぜ機械で縛れないか
「2 つのコードが似ている」ことは検出できても、それが
**「同じ理由で同じように変化する（本質的同一）」**のか
**「今はたまたま同じ（偶然の一致）」**なのかは、**ドメインの意図**を理解しないと判定できない。

### AI の判定手順
1. 共通化候補の 2 つ（以上）を取り出す。
2. **「これらは将来、同じ理由で同時に変わるか？」**を問う。
   - YES（同じビジネスルールに由来）→ 本質的同一。共通化してよい。
   - NO（別々の理由で変わりうる）→ 偶然の一致。共通化**しない**。分けたまま保つ。
3. 判断材料：
   - 2 つは**同じドメイン概念**を表しているか？
   - 片方の仕様変更が、もう片方に**波及すべきか**？ 波及してほしくないなら別物。
4. **3 回ルール**を併用：同じパターンが **3 箇所以上**で、かつ本質的同一のときに初めて共通化を検討する。
   2 箇所での先行共通化は原則しない。

### 判定例
- ❌ 「商品価格の表示整形」と「ユーザーポイントの表示整形」がたまたま同じ `formatNumber` だから共通化
   → 通貨記号やまるめ規則が別々に変わりうる。**偶然の一致**。分けるべき。
- ✅ 「注文合計の税計算」が 3 つのユースケースで完全に同じビジネスルール → `domain` の税計算サービスへ集約。
- ⚠️ 2 箇所で同じ → まだ共通化しない。3 箇所目が来てから本質的同一かを再判定。

### グレーゾーンの扱い
- SR-1（重複禁止）と**緊張関係**にある。
  - SR-1 は「同じ機能を二度作るな」、SR-3 は「偽の共通化をするな」。
  - **意味が同じなら SR-1 で再利用、意味が偶然同じなだけなら SR-3 で分離。**
- 判断の軸は常に **「同じ理由で変わるか」**。これで両者を切り分ける。

> 関連 Skill: `find-shared`（候補抽出）。抽出は機械的にできるが、**本質/偶然の判定は AI が SR-3 で行う**。

## SR-4. レイヤー越えの語彙汚染をしない（概念の漏れ）

**Rule**: あるレイヤーに、**そのレイヤーが知ってはいけない下位/外側の語彙**を持ち込まない。

### なぜ機械で縛れないか
依存方向（import の向き）は dependency-cruiser で縛れる。
だが「**語彙・概念の漏れ**」は import を伴わずに起きることがあり、**型チェックを通ってしまう**。
例：`domain` のメソッドが `statusCode: 404` を返す。HTTP を import していなくても、HTTP の概念が domain に漏れている。

### AI の判定手順
1. 対象ファイルがどのレイヤーに属するかを特定する。
2. そのレイヤーの**許される語彙**を確認する：
   - **domain**: ビジネス語彙のみ（`Post`, `like`, `OutOfStock`）。
     HTTP / DB / FW / UI の語彙は**禁止**（`statusCode`, `Request`, `@Column`, `Prisma`, `req`, `res`）。
   - **application**: domain 語彙 + ユースケースの調整語彙。インフラ詳細は禁止。
   - **FSD entities**: ドメイン語彙のみ。`shared` の技術語彙に依存しすぎない。
3. レイヤーに**不釣り合いな語彙**が混入していないか、**意味で**走査する。
4. 見つけたら「どの概念が、どのレイヤーに漏れているか」を指摘する。

### 判定例
- ❌ `domain/post/Post.ts` のメソッドが `{ statusCode: 409 }` を返す → HTTP 概念が domain に漏れ。
   → domain は `throw new PostAlreadyLikedError()`。HTTP 変換は `presentation` の責務。
- ❌ `domain/user/User.ts` に `@Entity()` `@Column()`（ORM デコレータ）→ 永続化詳細が domain に漏れ。
- ❌ FSD `entities/post/model` が `localStorage` を直接触る → 技術詳細（`shared` の責務）が entity に漏れ。
- ✅ domain はドメインエラーを投げ、presentation がそれを HTTP ステータスにマップする。

### グレーゾーンの扱い
- 「これはドメイン語彙か技術語彙か」が曖昧なケース（例：`id` は両方にある）。
- 判断軸：**その語彙はビジネスの人に通じるか？** 通じない（`statusCode`）なら技術語彙。
- 迷えば「語彙汚染の疑い：概念 X がレイヤー Y に漏れている可能性」と提示する。

## ルール間の関係（早見表）

| 状況 | 適用ルール | 判断の軸 |
|---|---|---|
| 似た機能を新規に書こうとしている | SR-1 | 意味が同じか？ → 同じなら再利用 |
| 1 ファイルが大きく/雑多になってきた | SR-2 | 一文に接続詞が要るか？ |
| 似たコードをまとめたくなった | SR-3 | 同じ理由で同時に変わるか？ |
| 下位/外側の語彙が上位に出てきた | SR-4 | その語彙はビジネスに通じるか？ |

> **SR-1 と SR-3 の交通整理**：
> 「意味が同じ」→ SR-1 で再利用。「偶然同じだけ」→ SR-3 で分離。
> 両者を分ける唯一の軸は **「同じ理由で変わるか」**。

## AI への上位指示（メタルール）

1. **根拠なき指摘をしない**。必ず「ファイル・箇所・理由」をセットで出す。
2. **断定より提示**。意味判断は誤りうる。グレーは「可能性あり、判断を仰ぐ」と人間に返す。
3. **ルールは増やしすぎない**。現在 SR-1〜SR-4 の 4 つ。追加は運用で必要が証明されてから、このファイルに明記する。
4. このファイルが Single Source of Truth。Skill / command はここを**参照**し、**複製しない**。

### SR の追加 / 撤去プロセス（メタルール 3 の運用）

SR セットは MPA の心臓であり、軽々に増減しない。増減するときは以下に従う。

- **追加条件**: 同種の意味的違反が、レビュー（[`50-enforcement.md`](./50-enforcement.md) の **L4**）で**複数回すり抜けた実績**を根拠とする。「あったら便利」では足さない。
- **新 SR の形式**: 既存テンプレ（**Rule / なぜ機械で縛れないか / AI の判定手順 / 判定例 / グレーゾーンの扱い**）に必ず従う。形式を外れた SR は追加しない。
- **追加時の同時更新（怠ると網に穴）**: 新 SR を足すなら、以下を**同時に**追加する。どれか一つでも欠けると、その SR は層のどこかをすり抜ける。
  - [`../examples/anti-patterns/`](../examples/anti-patterns/) に違反見本（`SR-N-<name>.md`）＋ [`anti-patterns/README.md`](../examples/anti-patterns/README.md) の対応表の 1 行。
  - [`checklists/before-merge.md`](./checklists/before-merge.md) の `R-N`（レビュー側）。
  - [`checklists/before-writing.md`](./checklists/before-writing.md) の `STEP`（生成側）。
- **撤去条件**: その SR が**機械検証可能になったら**、lint / dependency-cruiser（[`50-enforcement.md`](./50-enforcement.md) の **L3**）へ昇格させ、SR からは削除する。機械で縛れるものを意味判断に残さない（L3 が土台、SR は網）。
