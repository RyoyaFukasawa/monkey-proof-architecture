# 設計メモ：理想的なプロジェクトの進め方（タイムライン）

> **正直な線引き**：「🐵だけで完全に回る」は幻想。**コードは書けなくていいが、業務（ドメイン）が分かる人は要る**。
> その人が仕様をレビューする（フェーズ0）。実装の意味レビューはエンジニアが担う（フェーズ2）。
> AC・テスト・実装を全部 Claude が書く以上、機械（L3）が保証するのは**配置と体裁**まで。**業務的な正しさは人間レビューに残る**。
> なので凝った仕掛け（🐵の はい/いいえ 逆問診など）で人間レビューを代替しようとせず、**普通に人間がレビューする**。

## タイムライン

### フェーズ 0：仕様をつくる

| # | 誰 | やること | 縛る層 |
|---|---|---|---|
| 0-1 | **🐵** | 仕様作成スキルを叩き、仕様を話す（画面単位でも、どんな話し方でもいい） | — |
| 0-2 | **Claude** | ケイパビリティ単位に分解（横断ルールは glossary へ／未決は質問で潰す） | L1（SR-2） |
| 0-3 | **Claude** | `docs/spec/*.md` を生成。**受け入れ基準は1項目ごとに `AC-1` のID を振る**（front-matter ＋ 必須セクション） | — |
| 0-4 | **機械** | 仕様 lint：必須欠落／**各 AC が測定可能か（数値トークンの有無）**／`status:draft`／リンク切れ／**AC-id 必須** | **L3** |
| 0-5 | **Claude** | L3 が落ちたら自分で直す。直せない未決は🐵に自然言語で質問 | L4（自己レビュー） |
| 0-6 | **Claude** | 緑になったら spec PR を作成。**AC を業務の言葉で要約**して PR 説明に載せる（レビューしやすく） | — |
| 0-7 | **ドメインが分かる人** | spec PR をレビューし、**業務的に正しいか**を確認してマージ（コードは読めなくてよい／業務は分かる） | L4（人間） |

### フェーズ 1：仕様 → タスク（縦スライス issue）へ展開

> issue の粒度は **縦スライス1本＝1 issue＝1 PR**（例：`POST /invitations` の Controller→UseCase→Domain→Repo の流れ1本／
> Web の招待モーダル UI ＋ API 呼び出し1本）。1 ケイパビリティに複数 issue がぶら下がる（N:M の N 側）。
> Claude が1セッションで実装でき、L3（依存方向）も1本の中で完結チェックできる粒度。

| # | 誰 | やること | 縛る層 |
|---|---|---|---|
| 1-1 | **Claude** | spec（`spec-id`）を読み、**縦スライス単位の issue 群に分解**して起票（各 issue が `@spec` を指す） | L1（縦スライスの切り方） |
| 1-2 | **機械** | issue が GitHub Project（kanban/WBS）に自動で乗る（status＝Todo） | — |
| 1-3 | **人間** | issue 分割の妥当性を確認（縦スライスが太すぎ/細すぎないか）。★分解判断なので素通りリスクあり | L4（人間） |

### フェーズ 2：実装する

| # | 誰 | やること | 縛る層 |
|---|---|---|---|
| 2-1 | **🐵/開発者** | 実装スキルを叩き、issue を選択 | — |
| 2-2 | **Claude** | spec を読んで実装。`@spec` を付け `implemented-by` を機械更新。**各 AC に対応するテストを書き `@ac AC-1` を付与** | L1（SR-1〜4・配置） |
| 2-3 | **Claude** | ★実装中に **spec の不備が発覚したら止める**。issue に `blocked:spec` を貼り、フェーズ0へ差し戻す（spec無視の捻じ曲げ禁止） | L1（停止条件） |
| 2-4 | **機械** | コード L3：依存方向／命名／公開API／死コード ＋ spec↔実装リンク ＋ **AC↔テストの対称差（未カバー AC は fail）** | **L3** |
| 2-5 | **Claude** | 落ちたら直す。緑で実装 PR を作成 | L4（自己レビュー） |
| 2-6 | **エンジニア** | 実装 PR をマージ（コードの意味的妥当性をレビュー）。★ここは**業務だけでなくコードが分かる人**が要る | L4（人間） |

### フェーズ 3：状態が自動で閉じる

| # | 誰 | やること | 縛る層 |
|---|---|---|---|
| 3-1 | **機械** | PR マージで紐づく issue が自動クローズ（`Closes #n`） | L3 |
| 3-2 | **機械** | GitHub Project の status が自動で Done に | — |
| 3-3 | **機械** | 未実装の spec が一覧で見える（spec↔実装リンクから導出） | L3 |
| 3-4 | **機械** | **spec を後で改訂したら**、その AC を `@spec`/`@ac` で指すコードを逆引きし `spec-drift` issue を自動起票（spec→実装の追跡） | L3 |

## 人間ゲートの線引き（正直に）

「🐵だけで完全に回る」は諦める。要る人間は2種類だけ、それぞれ要求スキルが違う：

| ゲート | 誰 | 要求すること | 要求しないこと |
|---|---|---|---|
| **0-7 仕様レビュー** | ドメインが分かる人（PM・業務担当） | 業務的に正しいか判断できる | コードは読めなくてよい |
| **2-6 実装レビュー** | エンジニア | コードの意味的妥当性を判断できる | — |

- **入口（0-1 話す）も、できればドメインが分かる人**が望ましい（的外れな要望を Claude が真面目に spec 化してしまうため）。
- **完全な素人（何も分からない🐵）はレビュアーにしない**。レビューする人が分かっていないなら、どんな仕掛けでも素通りは防げない（＝詰み）。だから「業務が分かる」を最低ラインとして要求する。
