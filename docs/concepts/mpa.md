# 🐵Monkey-Proof Architecture — 思想

> **MPA = Monkey-Proof Architecture**
> 規律を内面化していない人間（新人・業務委託・将来の自分）と、規律を持たない AI エージェントの**両方**が、
> 「考えなくても」動かして壊れない **プロジェクト進行のフレーム**。

---

## 0. Monkey とは

> "Monkey-Proof" = 「猿でも壊せない」設計。

このドキュメントで **🐵（Monkey）** と呼ぶのは、**規律を内面化していない動かし手**のこと。具体的には：

- 規約を読んでいない新人・将来の自分
- 規律を持たない AI エージェント
- 急いでいて手を抜く誰か（≒人類全員）

🐵 は怠惰だったり悪意があるわけではない。**ただ規律を内面化していない**。MPA はこの 🐵 が動かしても壊れないことを目指す。

→ 逆に言うと、**規律を完全に内面化した人だけのチーム**には MPA は要らない（が、現実にそういうチームは存在するのだろうか）。

---

## 1. MPAとは

MPA は、**仕様 → 実装 → 運用までを通して、🐵（規律のない人・AI）が動かしても壊れないようにする** ための進行フレームである。

既存のものはすべて **「人間が規律を守る」前提**で設計されている。だが現実には規律は守られない。守れる人だけを前提にした規約は、人数が増えるほど、AI が混ざるほど、破綻する。

MPA の出発点は一つ：

> **「守れる人」を前提にしない。**

代わりに、規約を **2つの方法で強制** する。

1. **機械で縛れるものは機械で縛る**（lint / 型 / CI）
2. **機械で縛れない意味的制御は AI で縛る**（= semantic lint）

そして、この2つでも縛れないものは **正直に人間ゲートとして残す**。

---

## 2. 諦めること

何でもできるフレームではない。先に「これは諦める」を3つ書く。

### 🐵だけでは回らない

コードが書けない人だけで仕様から運用まで回すことはできない。最低でも次の2人は要る：

- **業務が分かる人** — 仕様が業務的に正しいかを見る
- **コードが分かるエンジニア** — 実装が意味的に正しいかを見る

何も分からない🐵はレビュアーにできない。**レビューする人が分かっていなければ、どんな仕掛けでも素通りする**。

### 意味的制御は完璧にはできない

- 機械検証（lint / 型）は **必ず止まる**。ルールに反していたら CI が落ちてマージできない。
- 意味的制御（同じ機能が既にないか・1ファイル1責務か等）は AI 任せでしかない。**たまにすり抜ける**。

だから MPA は「これさえあれば完璧」という関門を作らない。**何重にも重ねて、すり抜ける確率を下げる**

---

## 3. 原則(Principle)

MPA は5つの原則で立っている。番号は見出しの整理用で、本文では名前で呼ぶ。

### P1. 原本は一つ。何でも一つにする。

規約・仕様・タスク・進行表 — **プロジェクトに関わる情報はすべて、唯一の場所**に置く。複製しない。常に**参照する**。

- 二重管理は腐る
- 人間用ドキュメントと AI 用プロンプトも分けない（同じ原本を読む）
- AI に規約を「記憶から再生」させない（実ファイルを読ませる）

### P2. 機械で縛れるものは、必ず機械で縛る。

意味の理解を要さないものはすべて機械で落とす。**人間にも AI にも判断させない**。

- コード — 依存方向・命名・公開API・死コード（lint / 型  / knip）
- 仕様 — 必須項目の欠落・AC-id の有無・テンプレート逸脱（仕様 lint）
- タスク — issue テンプレ違反・spec 未参照・GitHub Projects（kanban / WBS / ロードマップ）に自動連携
- リンク — spec ↔ 実装 ↔ テスト ↔ issue の整合（CI で検証）

**機械で縛れるものまで AI に委ねるとコストが上がり、ブレが生まれる**。

### P3. 機械で縛れない意味的制御は、AI に任せる（= semantic lint）。

「同じ機能が既にないか」「仕様が業務的に重複してないか」のように、**意味の理解が要る判定**は AI に任せる。

MPA が広げているのは射程：**コードのレビューだけでなく、仕様・タスク・運用まで semantic lint で縛る**。

### P4. 採用する技術は、既に育ちきったものを使う。発明しない。

各フェーズで使う技術は、業界で実績があり・規約が明文化されていて・ツールが揃っているものだけを採用する。

- 仕様 — Markdown（Notion などの別サービスは基本的に使わない。使う場合も原本を一つにし、必ず参照形式にする）
- タスク — GitHub Issues + Projects / Conventional Commits
- コード — FSD / Clean Architecture（ドメイン層は DDD）/ monorepo

「AI 時代っぽい発明」を持ち込まない。**発明するのはメタレイヤー（強制の組み立て方）だけ**。

### P5. どれか一つに賭けない。重ねる。

機械チェック・AI チェック・人間レビューを**重ねて使う**。「これさえあれば大丈夫」という単独の関門は作らない。

これは**どのフェーズでも同じ**：

- 仕様 → 仕様 lint（機械） / 業務的重複チェック（AI） / 業務が分かる人がレビュー（人間）
- タスク → テンプレ違反検出（機械） / 粒度・重複チェック（AI） / 分解の妥当性をレビュー（人間）
- コード → lint / 型（機械） / semantic lint（AI） / エンジニアがレビュー（人間）

同じ AI は似たところで見落とすので、AI だけにも頼らない。
