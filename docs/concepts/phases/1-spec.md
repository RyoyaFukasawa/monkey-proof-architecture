# フェーズ1：仕様をつくる

← [workflow.md に戻る](../workflow.md)

## ゴール

業務的に正しい仕様を Markdown で固める。各受け入れ基準（AC）に **`AC-1` のような ID** を振り、後続のテスト・実装から参照できるようにする。

---

## このフェーズの入口

- 新機能を作りたい
- 既存機能を改修したい（既存仕様を改訂する）
- フェーズ4で `spec-drift` issue が起票された

---

## 流れ

| # | 誰 | やること |
|---|---|---|
| 1-1 | 🐵 | 仕様作成スキルを叩き、欲しいものを話す（画面単位でも、どんな話し方でもいい） |
| 1-2 | AI | ケイパビリティ単位に分解（横断ルールは glossary へ／未決は質問で潰す） |
| 1-3 | AI | `docs/spec/<spec-id>.md` を生成。**受け入れ基準は1項目ごとに `AC-1` の ID を振る**（front-matter ＋ 必須セクション） |
| 1-4 | 機械 | 仕様 lint：必須欠落／**各 AC が測定可能か**（数値トークンの有無）／`status:draft`／リンク切れ／**AC-id 必須** |
| 1-5 | AI | lint が落ちたら自分で直す。直せない未決は🐵に自然言語で質問 |
| 1-6 | AI | 緑になったら spec PR を作成。**AC を業務の言葉で要約**して PR 説明に載せる（レビューしやすく） |
| 1-7 | 👤 | spec PR をレビューし、**業務的に正しいか**を確認してマージ |

---

## 機械が縛るもの（仕様 lint）

意味の理解を要さないものはすべて機械で落とす：

- front-matter の必須項目（`spec-id` / `status` / `owner` 等）の欠落
- AC ごとに ID（`AC-1`, `AC-2`, …）が振られているか
- 各 AC が **測定可能か**（曖昧な「使いやすい」「速い」ではなく、数値や明確な条件で書かれているか）
- `status: draft` のまま放置されていないか
- 内部リンク切れ
- 用語が glossary に登録されているか

---

## AI が縛るもの（semantic lint）

機械では判定できない意味的なものは AI が見る：

- **仕様の業務的重複** — 既に書かれた他の spec と意味が被ってないか
- **粒度** — 大きすぎ・小さすぎないか
- **用語の一貫性** — 同じ概念が違う名前で呼ばれていないか
- **AC の妥当性** — 受け入れ基準が業務上の検収条件として適切か

---

## 人間が見るもの（人間ゲート 1-7）

| ゲート | 誰 | 判断すること |
|---|---|---|
| **1-7 仕様レビュー** | 業務が分かる人（PM・業務担当） | 業務的に正しいか・抜けがないか |

コードは読めなくてよい。**業務が分かっている**ことだけが要件。

## このフェーズの成果物

- **`docs/spec/<spec-id>.md`** — 仕様本体
  - front-matter（`spec-id` / `status` / `owner` 等）
  - 必須セクション（背景 / ゴール / AC / 用語）
  - **各 AC に `AC-1` の ID が振られている**
